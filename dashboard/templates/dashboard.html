Experiment 4 — how much does the answer depend on how we asked?
The other three experiments ask how fast, how large and how accurate each simulator is. This one asks something different: whether those answers survive a change in the question. A benchmark whose ranking flips when the network size or the metric changes has not produced a recommendation, it has produced an artefact of its own configuration — and knowing which of the two you are holding is the point.
The statistic is Kendall's τ, the rank correlation between two orderings of the same backends. τ = 1 means the two orderings agree exactly, 0 means they are unrelated, and −1 means one is the reverse of the other. Rank correlation is used rather than a comparison of the values themselves because the claim under test is about the order a reader would act on, not the magnitudes.
Does the ordering depend on the network size measured?
Each tile compares the runtime ordering at that network size against the ordering at the largest size measured. If a benchmark reported only one size, this is how much its recommendation would have differed.
Does the ordering depend on the metric chosen?
Each tile compares the ordering under that metric against the ordering by runtime, both at the largest network size.
Objective O2 — the energy proxy against the EFLOP metric
The stated objective is to assess how far the utilisation-weighted energy proxy agrees with an operation-count metric, by rank correlation.
Do the simulators agree on the answer?
Before any timing comparison means anything, the implementations have to be simulating the same network. Each backend's output firing rate is compared against the plain-NumPy validation control of the identical model. A simulator that is fast because it is solving an easier problem would show up here.

What this dashboard does not claim
 
The energy figure is a proxy, not a measurement. It is runtime × CPU utilisation × a configured TDP value, and is comparable only within this machine and this session. It is not joules at the wall socket.
The simulators are not solving identical problems. The tensor-based libraries run a discrete recurrence; the simulators integrate an ODE. The equivalence view bounds how far apart that lets the answers drift, but a runtime advantage is partly a cheaper problem, not purely better engineering.
One hardware platform, by design. Holding the machine fixed is what allows a difference in runtime to be attributed to a difference in the simulator rather than to the hardware it happened to run on — that control is the basis of the comparison. The consequence is that absolute timings are specific to this platform; what carries across is the ordering, and the Sensitivity view reports how far even that holds. Running the same harness on GPU hardware is identified in the thesis as the next extension of this work.
